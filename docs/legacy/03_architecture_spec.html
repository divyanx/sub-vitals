§ 01

System topology

BrandPulse is a single Devvit app exposing two render surfaces, six event listeners, three scheduled jobs, and a REST API for the webview dashboard. All persistence is Devvit Redis (auto-scoped per installation). External AI providers are reached over HTTP with App-scope secrets.

§ 02

Module contract

Every module is a TypeScript object implementing BrandPulseModule. The contract is intentionally narrow: it gives modules optional hooks for every event surface, plus optional menu items and API routes. Modules never touch Devvit.add* directly — registration is centralized in main.tsx.

export interface BrandPulseModule {
  readonly name: string;
  readonly description: string;
  readonly tier: 'core' | 'pro' | 'enterprise';

  // Feature-flag check (reads from Installation settings)
  enabled(ctx: Context): Promise<boolean>;

  // Optional event handlers — only those the module needs
  onAppInstall?(event, ctx): Promise<void>;
  onPostSubmit?(event, ctx): Promise<void>;
  onCommentSubmit?(event, ctx): Promise<void>;
  onPostUpdate?(event, ctx): Promise<void>;
  onModAction?(event, ctx): Promise<void>;

  // Optional surfaces the module owns
  menuItems?(): Devvit.MenuItem[];
  apiRoutes?(app: Hono): void;
  schedulerTasks?(): SchedulerTask[];
}
Why a uniform contract

It makes adding/removing modules a one-line change in main.tsx. It also gives the dispatcher a single place to enforce failure isolation: if one module throws on onPostSubmit, the others still run because the dispatcher wraps each handler in try/catch. No cascading failures from one buggy module.

§ 03

Event flow: PostSubmit

The most common path. When a user posts in a subreddit where BrandPulse is installed, the following sequence fires:

1.Reddit → Devvit Platform : PostSubmit event emitted
2.Devvit Platform → main.tsx trigger : onEvent(event, ctx) invoked
3.main.tsx → dispatcher.dispatch : dispatch('onPostSubmit', event, ctx)
4.dispatcher → [all modules] : Promise.all(modules with handler)
5a.contact-drivers → Redis : SET bp:tag:{postId} · ZADD bp:dr:idx · update rollup
5b.sentiment → lexicon scorer : score = lexicon(text)
5c.sentiment → Redis : SET bp:sent:{postId} · update daily rollup
5d.pii-guardian (P2) → regex + LLM : scan for PII; if found, modmail or auto-redact
6.dispatcher → main.tsx : all handlers settled (isolated errors logged)
7.main.tsx → Devvit Platform : 200 OK

Total budget for the entire fan-out: ~1–3 seconds (Devvit allows up to ~30s per trigger but you should aim for <5). Lexicon-based sentiment is sub-ms. Redis writes are ~5ms each. The expensive path is Phase 2's LLM-based AI tagging — that one runs async after we acknowledge the trigger.

§ 04

Storage schema

All Redis keys are prefixed with bp: and built via the K helper in src/shared/storage.ts. The schema is intentionally flat — no embedded JSON trees that require read-modify-write at scale.

KeyTypeOwner moduleCardinality
bp:tx:{sub}JSONcontact-drivers1 per sub
bp:tag:{postId}JSONcontact-drivers1 per tagged post
bp:dr:idx:{sub}:{driverId}ZSETcontact-drivers1 per driver per sub
bp:dr:roll:{sub}:{date}JSONcontact-drivers1 per day per sub
bp:ag:{sub}:{user}JSONagent-verification1 per agent
bp:ag:list:{sub}ZSETagent-verification1 per sub
bp:sent:{contentId}JSONsentiment1 per scored content
bp:sent:roll:{sub}:{date}JSONsentiment1 per day per sub
bp:sent:cd:{sub}:{postId}STRING + TTLsentimentcooldown, 4h TTL
bp:rsp:{postId}JSONresponse-analytics (P2)1 per post
bp:rsp:open:{sub}ZSETresponse-analytics (P2)1 per sub
bp:pii:log:{sub}ZSETpii-guardian (P2)1 per sub
bp:perm:mod:{sub}:{user}STRING + TTLpermissions5-min cache
Scaling note

Daily rollups use a read-modify-write pattern because Devvit Redis doesn't expose HINCRBY with auto-create-on-miss the way standalone Redis does. For Phase 2, swap to a hash per day (HSET bp:dr:roll:{sub}:{date} {driver} {count} + HINCRBY) to avoid the RMW race under bursty load.

§ 05

Integration surfaces

BrandPulse exposes itself through every surface Devvit offers, deliberately. Mods who prefer in-feed actions get menu items. Mods who want full analytics get the dashboard. Teams running Sprinklr or Khoros get the REST API. Each surface is independently usable.

Surface 1 · Native Reddit UI (Menu Items + Custom Posts + Modmail)

  • Post menu: Tag Issue, View Sentiment Trail, Scan for PII
  • Comment menu: Mark/Remove Verified Agent
  • Subreddit menu: Open BrandPulse Dashboard
  • Custom Post: pinned Daily Pulse digest, auto-updates every morning
  • Modmail: sentiment escalation alerts, weekly digest, SLA breach notifications

Surface 2 · WebView Dashboard (Devvit Web)

  • Vite-built React app served as iframe content
  • Tabs: Overview · Contact Drivers · Sentiment · Agents · Settings
  • Talks to the Hono backend via fetch on same origin
  • Native-feel styling: IBM Plex Sans, dark theme default, Reddit-orange accents, restrained color

Surface 3 · REST API (for external tools)

Same Hono server that powers the webview also exposes the public API. Same routes, same auth model. External tools (Sprinklr, Khoros, in-house CX dashboards) hit endpoints like:

GET  /api/agents
GET  /api/drivers/volume?from=2026-05-01&to=2026-05-16
GET  /api/drivers/:driverId/posts
POST /api/drivers/tag
GET  /api/sentiment/rollup
GET  /api/dashboard/summary

Phase 2 hardens this with HMAC-signed requests for non-mod consumers (CI bots, external dashboards). Until then, all routes require mod status via requireMod().

Surface 4 · Settings (App + Installation scope)

  • App-scope: openai-api-key, gemini-api-key — managed via devvit settings set CLI, encrypted at rest, never exposed to mods
  • Installation-scope: agent whitelist, taxonomy JSON, sentiment threshold, PII auto-redact toggle, SLA window — managed per-subreddit by that sub's mod team
§ 06

Permissions model

Three principal types interact with BrandPulse:

PrincipalIdentificationAllowed surfacesMutation rights
Developer (you)Devvit CLI loginApp settings via CLISecrets, app deployment
Subreddit moderatorctx.reddit.getModerators()All menu items, dashboard, installation settingsTag posts, mark agents, configure
Regular Reddit userDefaultCustom Post (Daily Pulse) read-only viewNone

Every mutating handler calls requireMod(ctx) first. The function checks the current user against the subreddit's moderator list and caches the result for 5 minutes per (sub, user) pair to avoid hammering Reddit's API on repeat actions.

async function requireMod(ctx: Context): Promise<boolean> {
  const ok = await isCurrentUserMod(ctx);
  if (!ok) {
    ctx.ui.showToast({ appearance: 'neutral', text: 'Mod-only action.' });
  }
  return ok;
}

// Usage in every mod menu handler:
onPress: async (event, ctx) => {
  if (!(await requireMod(ctx))) return;
  // mutation logic
}
§ 07

External integrations

BrandPulse is designed so a Sprinklr-style CX platform can consume Reddit signal from it without writing Reddit-specific code.

Outbound webhooks (Phase 2)

Per-installation setting accepts a webhook URL. On every interesting event (post tagged, sentiment alert, SLA breach), BrandPulse POSTs a normalized JSON payload:

{
  "event": "sentiment.escalation",
  "sub": "sonos",
  "postId": "t3_abc123",
  "url": "https://reddit.com/r/sonos/comments/abc123",
  "negativeCommentCount": 7,
  "sample": 10,
  "timestamp": 1747000000000
}

Pull API (Phase 2)

The Hono server exposes the same routes the webview uses, but reachable from outside via a Devvit-issued bearer token. External tools can poll /api/drivers/volume, /api/sentiment/rollup, etc., and ingest the data into their own warehouses.

CSV export (Phase 1.5)

Dashboard offers a "Download CSV" button per view. Drives Excel users (CX ops teams) without forcing them to use the dashboard. Cheap to ship, high perceived value.

Sprinklr strategy

Don't try to formally integrate. Make BrandPulse data trivially ingestible (CSV export + bearer-token REST). Sprinklr customers can wire it themselves in 30 minutes. Avoids any partnership negotiation while still capturing the enterprise CX-tooling demand.

§ 08

Failure modes & mitigation

FailureImpactMitigation
One module throws on trigger Could break all event processing Dispatcher wraps every handler in try/catch; logs and continues
OpenAI / Gemini API outage AI-powered modules degrade Phase 2 modules fall back to lexicon/regex baselines; alert via modmail if sustained outage
Settings scope confusion App can't read configured value Document scope decisions; never change scope after deploy (known Devvit bug)
Redis read-modify-write race Rollup counts could undercount Phase 2: migrate to Redis HINCRBY-style atomic increments
Trigger handler timeout Devvit kills the handler Keep handlers under 5s; defer expensive work (LLM calls) to scheduler jobs
Mod permission check fails (Reddit API hiccup) Mod action incorrectly rejected 5-min permission cache; show clear error toast on cache miss + API failure
ModAction trigger floods the dispatcher Burst load on Redis Handler must filter action type early; only react to relevant types

Phasing plan

Phase 1 · Hackathon MVP (May 16–27)

  • Agent Verification (settings whitelist + menu actions)
  • Contact Drivers (manual tagging + keyword auto-suggest)
  • Sentiment Dashboard (lexicon scoring + escalation modmail)
  • Daily Pulse custom post
  • WebView dashboard (Overview, Drivers, Agents tabs)

Phase 2 · Pro tier (June–July 2026)

  • PII Guardian (regex + LLM redactor)
  • Response Analytics (SLA tracking via agent comment timestamps)
  • AI sentiment upgrade (LLM judge for ambiguous cases)
  • Outbound webhooks
  • CSV export

Phase 3 · Enterprise tier (Q3 2026)

  • AI Content Detector (perplexity + LLM judge)
  • Harassment pattern alerts
  • Bulk historical import (last 90 days)
  • Quality Management scorecards (Sprinklr-style agent QA)
  • Bearer-token REST API for external CX tools
